Choose `cratis-aspire` when you want an app host to start Chronicle, its database, and your backend together. It composes the C# [Cratis Web Application](/templates/cratis-web/) with [Aspire](https://learn.microsoft.com/en-us/dotnet/aspire/) instead of a `docker-compose.yml`; the event, command, query, and React slices stay in the web project. You still start Vite separately for frontend development.

You need the .NET 10 SDK, Docker (the app host runs Chronicle and any database as containers), and Node.js `^20.19.0` or `>=22.12.0` with a package manager for the frontend. The commands below use yarn. [Install the templates](/templates/getting-started/#install-the-templates) first if the package is not installed.

```bash
dotnet new cratis-aspire -n MyStore
```

## Options

| Option | Values | Default |
| --- | --- | --- |
| `--Database` | `MongoDB`, `PostgreSQL`, `MsSql`, `SQLite` | `MongoDB` |
| `--Framework` | `net10.0` | `net10.0` |
| `--SkipAiUpdateInstructions` | `true`, `false` | `false` |

Leave MongoDB selected for the first run. The app host runs the Chronicle development image with development client credentials; use it only on a trusted development machine. Use disposable sample data: the generated default MongoDB composition does not request a persistent data volume.

Unlike `cratis`, this template has no `--packageManager` option and does not install frontend dependencies for you. The run procedure below installs them in the web project; alternative database creation is described after that procedure.

## What you get

The web application, app host, and shared service defaults each have their own project. Change application behavior in the web project and local service wiring in the app host:

| Project | Role |
| --- | --- |
| `<App>` | The full-stack web application: Arc backend, Chronicle client, React frontend, and the same `SomeModule/SomeFeature` slices |
| `<App>.Composition` | The Aspire app host: starts Chronicle with `AddCratisChronicle()` and any database, launches the backend, and passes it the Chronicle and read-model connections |
| `<App>.Infrastructure` | Shared service defaults: OpenTelemetry, health checks, resilience, and service discovery |

## Run it

`dotnet new` creates a `MyStore` solution folder with the web project in a nested `MyStore` folder. The two folders have different jobs: install frontend dependencies in MyStore/MyStore, then return to the solution folder to launch the app host. Leave that terminal running; it hosts the backend and containers, not Vite:

```bash
cd MyStore          # the solution folder
cd MyStore          # the web project
yarn install
cd ..
dotnet run --project MyStore.Composition
```

Aspire starts the containers and backend and prints the dashboard address with a one-time login token, for example `https://localhost:57075/login?t=…`. Open the link from your terminal because the port changes between runs. Use the backend and Chronicle resource logs there to investigate startup or connection failures; reaching the dashboard is not yet a check of the application.

In a second terminal, run `yarn dev` from the nested `MyStore` web-project folder: MyStore/MyStore relative to where you scaffolded. Vite serves on `http://localhost:9000` and forwards `/api`, `/.cratis`, and `/swagger` to `http://localhost:5000`. Open **Demo**, select **Register**, and enter a name. The backend reactor logs `Registered: <name>`; look for the name in the list to check the projected read result separately. Follow [the web template's sample slices](/templates/cratis-web/#the-sample-slices-teach-the-conventions) to trace that command, event, and query in the web project.

When you finish, stop Vite and then the app host in their terminals. This setup is managed by the app host, not Compose; do not apply the plain web template's Compose cleanup commands to it.

Choose a different database at creation time, in place of the first scaffold command, not as another command inside the solution you just created. With a database other than MongoDB, the app host starts a PostgreSQL or SQL Server container (or, for SQLite, uses a `chronicle-data` folder next to the solution), stores Chronicle's data there, and gives the backend a connection to the `chronicle+<event store>` database Chronicle projects read models into. The backend reads them through Entity Framework Core:

```bash
dotnet new cratis-aspire -n MyStore --Database PostgreSQL
```

## What it is for

Use the Composition project when you need to change which services start together or how their connections reach the backend. The web project still owns the sample slices and frontend; changing an application feature does not require moving it into the app host. If you prefer to start the backend and containers separately, use the plain [Cratis Web Application](/templates/cratis-web/) template.

## AI assistance

AI assistance is optional and separate from starting the application. The scaffolded solution includes a `.cratis/ai.json` selecting the `cratis/application/csharp` profile with the C# and TypeScript languages. If you want that guidance, install the [Cratis CLI](/cli/) and run this from the outer MyStore solution folder, not the nested web project:

```bash
cratis ai update
```

That installs the AI rules, skills, and harness integration for the selected coding agents (`AGENTS.md` plus `.claude/`, `.cursor/`, `.github/`, `.opencode/`, and `.pi/`) and records what it installed in `.cratis/ai.manifest.json`. `dotnet new` prints this reminder after scaffolding; `cratis new` runs the update for you. Running it again refreshes only Cratis-managed files. See the [CLI AI documentation](/cli/ai/) for the full command reference.
