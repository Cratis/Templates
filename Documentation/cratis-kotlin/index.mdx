Start with a Kotlin application that registers a named item and shows it in a React list. The `cratis` template supplies a Spring Boot backend, a React frontend, and local infrastructure. Cratis Arc exposes the commands and queries over HTTP; Cratis Chronicle stores the events behind the listing. First run the sample, then follow its command and read model to see how the pieces connect.

## Before you begin

- **JDK 17.** The build uses a Gradle Java toolchain pinned to 17 and does not download one, so a JDK 17 must be installed where Gradle can find it, for example through `JAVA_HOME`. A newer JDK on its own fails with `Cannot find a Java installation on your machine … matching: {languageVersion=17 …}`.
- **Docker** with the Compose plugin, for the local Chronicle kernel.
- **Node.js `^20.19.0` or `>=22.12.0`** and yarn, pnpm, or npm for the frontend.

The .NET SDK is needed only if you scaffold with `dotnet new`; the generated project builds with the bundled Gradle wrapper.

The run steps below use the default MongoDB storage and yarn package manager. Choose different scaffold options only if you need them; the reference is under [Options](#options).

Choose one scaffolding tool. For `dotnet new`, run:

```bash
dotnet new install Cratis.Templates
dotnet new cratis --language Kotlin -n MyStore
```

Alternatively, install the [Cratis CLI](/cli/) and use its scaffold command instead:

```bash
cratis new cratis --language kotlin -n MyStore -o MyStore --allow-scripts yes
```

`Cratis.Templates` includes the Kotlin template; `Cratis.Templates.Kotlin` publishes the same template on its own. There is no `cratis-kotlin` short name.

## Run it

Before starting the backend, keep it local: Spring Boot listens on every interface by default. Set `server.address=127.0.0.1` in `application.properties`. The generated `docker-compose.yml` already binds its published ports to `127.0.0.1`.

Start Chronicle in Docker, then build the backend before starting the frontend. The frontend's `Api` imports point to `build/generated/arc-proxies/`, the Arc Gradle plugin's configured output directory, so the backend build comes first.

```bash
cd MyStore
docker compose up -d        # Chronicle kernel and Aspire dashboard
./gradlew build             # compiles and generates the TypeScript proxies
yarn install                # skip if the scaffold already installed dependencies
./gradlew bootRun           # backend on http://localhost:8080
```

In a second terminal opened in `MyStore`, start the frontend:

```bash
yarn dev
```

Vite serves the frontend on `http://localhost:9000`, opens it in your browser, and forwards `/api` and `/.cratis` to the backend. Open **Demo**, choose **Register**, enter a name, and submit it. The expected result is that name appearing in the list. To follow the same registration without the frontend, use the command and query requests under [The sample slices teach the conventions](#the-sample-slices-teach-the-conventions).

When the helper exits, whether you press Ctrl+C or a step fails, it runs `docker compose down`. This removes the containers and, with the default MongoDB storage, every event and read model. Use the manual steps with `docker compose stop` when you want to keep data between runs.

Instead of the manual steps, use `./run.sh` to start Chronicle, build the backend, and launch the frontend and backend from one terminal.

The helper tries yarn and falls back to npm. `./run.sh --no-frontend` starts only Chronicle and the backend.

The project includes a `.yarnrc.yml` that sets `nodeLinker: node-modules`, so Yarn 2 and later install into `node_modules` instead of Plug'n'Play, which the TypeScript 7 compiler cannot resolve. npm, pnpm, and Yarn 1 ignore the file.

## The sample slices teach the conventions

Start with `Register`: its `handle()` returns a `Registered` event containing the name. The command does not build the listing itself. This excerpt from `registration/Registration.kt` omits the event and reactor declared in the same file:

```kotlin
@Command
@AllowAnonymous
data class Register(
    @CommandKey val id: SomeId,
    val name: SomeName
) {
    fun handle(): Registered = Registered(name)
}
```

`SomeId` wraps the command's string identity. Its two `ConceptAs<String>` contracts expose that value to Arc and Chronicle. The event carries the name; the reducer takes the listing's `id` from the event context, so it refers to the same event source as the command key.

To put the registered name on screen, the reducer builds a `Listing` from the `Registered` event and its event-source identity. The query reads those stored listings through `IEventStore`. This excerpt from `listing/Listing.kt` omits the reducer:

```kotlin
@ArcReadModel
@ChronicleReadModel
@AllowAnonymous
data class Listing(
    val id: String = "",
    val name: SomeName = SomeName("")
) {
    companion object {
        @JvmStatic
        @Path("/api/listings")
        suspend fun all(
            @FromServices eventStore: IEventStore
        ): List<Listing> = eventStore.readModels.getInstances(Listing::class)
    }
}
```

The scaffold's `ChronicleConfiguration.kt` supplies an explicit list of the sample event, read model, reducer, and reactor. With the backend running, use the requests below to submit the command and read the listing without the React frontend.

```bash
curl -sS -X POST http://localhost:8080/api/register \
    -H 'Content-Type: application/json' \
    -d '{"id":"'$(uuidgen)'","name":"Cratis"}'

curl -sS -X QUERY http://localhost:8080/api/listings \
    -H 'Content-Type: application/json' \
    -d '{"arguments":{}}'
```

The first call returns `"isSuccess":true`. The second returns the listing in `data`, for example `[{"id":"…","name":"Cratis"}]`. `GET /api/listings` returns the same result.

## Options

| Option | Values | Default |
| --- | --- | --- |
| `--Database` | `MongoDB`, `PostgreSQL`, `MsSql`, `SQLite` | `MongoDB` |
| `--packageManager` | `yarn`, `pnpm`, `npm`, `none` | `yarn` |
| `--SkipAiUpdateInstructions` | `true`, `false` | `false` |

The application code is the same for every database, because the Chronicle kernel persists the read models. `--Database` changes how the Chronicle container in `docker-compose.yml` stores its data (embedded MongoDB, a PostgreSQL or SQL Server container, or an SQLite file on a named volume) and switches the default read-model sink in `ChronicleConfiguration.kt` between MongoDB and SQL:

```bash
dotnet new cratis --language Kotlin -n MyStore --Database PostgreSQL
```

## Versions

The Arc Gradle plugin (`io.cratis.arc`) and `io.cratis:cratis`, the one dependency that bundles Arc, its Spring Boot wiring, and the Chronicle client, are requested as `latest.release`. Gradle resolves both requests when it builds; `latest.release` does not pin a reproducible pair in this file. Gradle caches a dynamic version for up to 24 hours by default; `./gradlew build --refresh-dependencies` picks up a newer release immediately.

For a reproducible or production build, replace `latest.release` with the exact version you tested, keeping the plugin and the `io.cratis:cratis` dependency on the same version, or enable Gradle dependency locking.

The rest of the build is pinned:

| Dependency | Version | Where |
| --- | --- | --- |
| Kotlin | 2.4.20 | `build.gradle.kts` |
| KSP | 2.3.12 | `build.gradle.kts` |
| Spring Boot | 4.1.1 | `build.gradle.kts` |
| Java toolchain | 17 | `build.gradle.kts` |
| Gradle | 9.1.0 | `gradle/wrapper/gradle-wrapper.properties` |

`build.gradle.kts` also pins `kotlinx-coroutines-core` to the version the Cratis libraries are compiled against, because Spring Boot's dependency management would otherwise select an older one that fails at startup.

## Troubleshooting

- **`Cannot find a Java installation … languageVersion=17`.** Install a JDK 17 and point `JAVA_HOME` at it.
- **`Cannot find module` during the frontend build.** Yarn 2 or later installed with Plug'n'Play because `.yarnrc.yml` is missing (projects scaffolded from earlier template versions do not have one). Add one containing `nodeLinker: node-modules` and run `yarn install` again.
- **Port 8080 or 35000 is already in use.** Stop the other process, or move the service. For the backend, set `server.port` in `application.properties` and update the two `http://localhost:8080` proxy targets in `.frontend/vite.config.ts`. For Chronicle, change the host side of the mapping in `docker-compose.yml` and point `cratis.chronicle.connection-string` at the new port.
## AI assistance

If you want coding-agent guidance, the scaffolded project includes a `.cratis/ai.json` selecting the `cratis/application/kotlin` profile with the Kotlin and TypeScript languages. After `dotnet new`, make sure the [Cratis CLI](/cli/) is installed, then run:

```bash
cratis ai update
```

`cratis new` runs this step for you. See the [CLI AI documentation](/cli/ai/) for the full command reference.
